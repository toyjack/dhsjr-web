# DHSJR MCP Server 改进开发规格书

**项目名称：** DHSJR MCP — AI-Native Research Interface  
**目标仓库：** `toyjack/dhsjr-web`  
**生产网站：** https://dhsjr.kojisho.com  
**MCP Endpoint：** https://dhsjr.kojisho.com/api/mcp  
**文档版本：** 1.0 Draft  
**制定日期：** 2026-10-16  
**开发方式：** Codex / Claude Code 分阶段实施  
**项目状态：** 现有 MCP 已实现，进入功能完善与质量保证阶段

---

# 1. 项目背景与目标

## 1.1 项目背景

DHSJR（資料横断的な漢字音・漢語音データベース）是面向日本历史汉字音、汉语音研究的跨文献数据库。

现有系统提供基于 Next.js 的 Web 检索界面，并通过 Supabase / PostgreSQL 提供数据查询，部分全文检索使用 PGroonga。

项目已实现基于 Model Context Protocol（MCP）的只读服务器，供 ChatGPT、Claude 及其他支持 MCP 的 AI 客户端调用。

目前 MCP 已实现基本查询、详细检索、单字记录、汉语记录与文献书目信息获取。

本次开发不是重建 MCP，而是完善现有功能，使其能够作为 Web 检索界面的功能性替代接口。

## 1.2 核心目标

最终用户应当能够直接通过自然语言向 AI 提出研究问题，而不必手动访问 DHSJR 网站完成检索。

典型问题包括：

- 检索「東」字在 DHSJR 各文献中的汉字音资料。
- 比较「經」在不同资料中的仮名注和声点。
- 检索某部文献中所有具有特定声点的记录。
- 查找包含特定反切或類音信息的单字。
- 获取某一汉语的全部构成汉字及其音注。
- 获取检索结果对应的书目、资料内位置和原始资料链接。
- 根据数据库的实际记录制作带出处的研究用汇总表。

对于这些任务，AI 应能自主选择 MCP 工具、进行必要的连续查询，并以可核验的方式组织结果。

## 1.3 核心设计原则

1. **功能等价：** MCP 与 Web UI 在相同查询语义下应取得相同记录。
2. **结果可靠：** 不得因为排序、分页、正字处理或错误处理导致数据遗漏。
3. **学术可信：** 保留原始字形、音注、声点、反切、资料内位置等研究信息。
4. **出处可追溯：** 每条研究记录均可追溯到 DHSJR 中的原始记录。
5. **AI 易用：** Tool Description、Schema、返回结果适合 AI 自动调用。
6. **Token 效率：** 避免返回不必要的重复信息，但不得牺牲研究数据的完整性。
7. **向后兼容：** 优先保持既有 MCP 客户端及 Web UI 的行为不变。
8. **共用业务逻辑：** Web 和 MCP 应尽量复用数据库查询层，而非各自维护查询规则。

## 1.4 非目标

本项目不包含：

- 重做 DHSJR 网站 UI。
- 更换 Next.js、Supabase 或 PostgreSQL 技术栈。
- 全面重建数据库结构。
- 让 AI 自主修改 DHSJR 研究数据。
- 开发独立的 AI 聊天网页。
- 新建与既有功能重复的搜索工具。
- 自动对尚无可靠对应关系的文献图片进行文字定位。
- 将数据库原始记录交由 LLM 自行补全或推测。

优先复用现有六个 MCP 工具。

## 2.2 当前 MCP 工具

|---|---|---|
| `search_all` | 跨字段全文检索 | 保留并完善 |
| `search_detail` | 多条件字段检索 | 保留并重点完善 |
| `list_books` | 收录资料一覧 | 保留 |
| `get_book` | 获取资料书目信息 | 保留并强化出处 |

`dhsjr://book/{book_id}`

## 2.3 当前查询语义

已知现有实现中：

- `search_all` 使用 PGroonga RPC，并在部分失败情况下回退到 `ILIKE`。
- `search_detail` 使用 Supabase 查询构造器执行字段检索。
- `character` 和 `book_id` 使用精确匹配。
- `word`、`kana`、`shoten`、`fanqie` 等字段使用部分匹配。
- 多个详细检索条件采用 AND 组合。
- MCP 默认每页20条，最大50条。
- 单字与汉语详细查询复用既有数据库访问逻辑。
- MCP 返回文本摘要和 JSON 字符串。
- 部分结果包含详细页面、汉语页面和书目页面的 URL。

开发时必须保留已确认的业务语义，不能因为接口优化而擅自修改检索定义。

# 3. 当前问题与调查任务

以下分为代码已确认的问题和需要通过测试确认的风险。

## 3.1 已确认问题

### ISSUE-001：详细检索缺少明确排序

**级别：P0**

`src/lib/db.ts` 中的 `search()` 当前使用范围分页，但没有指定完整、稳定的排序规则。

这意味着不同分页请求可能出现不稳定顺序。

修改要求：

- 为详细检索定义确定性的排序规则。
- 排序键必须包含可唯一确定记录顺序的最终键。
- Web 和 MCP 共同使用相同排序。
- 不得仅在 MCP 返回后进行数组排序。

初步建议：

1. `book_id`
2. `index_in_book`
3. `character_id`

实际实现必须检查字段类型、排序规则、数据库原始列名及唯一性。

如果资料内序号为字符串，应特别验证数字顺序和字典序是否一致。

### ISSUE-002：缺少标准化的 MCP structuredContent

**级别：P1**

当前 `textResult()` 将摘要及序列化 JSON 放入文本内容块。

修改要求：

- 验证已安装 MCP SDK 对 `structuredContent` 与 `outputSchema` 的支持。
- 在兼容旧客户端的前提下，增加机器可读的结构化返回值。
- 不得直接删除旧客户端依赖的文本内容。
- 为结果定义可验证的 Schema。

### ISSUE-003：检索结果包含一定程度的重复数据

**级别：P1**

现有实现同时提供逐条文本摘要和包含记录字段的 JSON 字符串。

需要优化：

- 支持精简的检索结果模式。
- 保留可获取完整字段的途径。
- 减少重复的记录内容。
- 验证不同 MCP 客户端的兼容性。

### ISSUE-004：返回 URL 依赖站点环境变量

**级别：P1**

当前 URL 构造依赖 `NEXT_PUBLIC_SITE_URL`，未配置时可能返回相对路径。

修改要求：

- 公开部署环境中必须返回可直接访问的绝对 URL。
- 保持对本地开发环境的支持。
- 检查国际化路由及重定向。
- 不能将测试域名硬编码到业务逻辑中。

## 3.2 待验证风险

### ISSUE-005：全文检索与回退检索的行为差异

**级别：P0，待验证**

PGroonga 与 `ILIKE` 可能在以下方面存在差异：

- 异体字处理
- 全角半角处理
- 匹配字段
- 匹配结果数量
- 搜索结果优先级
- 排序
- 特殊字符

必须首先检查 SQL 函数与现有回退实现。

不得假定两者在所有情况下完全等价。

如果无法保证等价，应明确向 MCP 调用方表示实际使用的检索后端及其局限，而非悄然提供语义不同的结果。

### ISSUE-006：新字体与旧字体检索一致性

**级别：P0，待验证**

当前 `search_all` 和 `search_detail` 使用不同检索方式。

应测试：

- `経` / `經`
- `医` / `醫`
- 其他数据库实际存在的代表性异体字

需要区分以下概念：

- 正字见出し
- 原文出現形
- 检索时的字形规范化
- 历史字形的学术差异

不得使用未经学术确认的 Unicode 规范化规则将全部异体字强制合并。

对于字形不一致的检索结果，必须能够区分“原文记录的实际字符”和“用于检索匹配的形式”。

### ISSUE-007：特殊字符及异常参数

**级别：P1，待验证**

检查含有 `%`、`_`、`,`、括号及其他特殊字符的查询。

重点检查：

- `ILIKE` 的通配符行为。
- Supabase `.or()` 的条件字符串构造。
- 空字符串与空白字符串。
- 非法页码。
- 超出允许范围的每页记录数。
- 过长查询词。
- 超出实际范围的页码。
- 数据库异常与超时。

应避免用户输入意外改变检索结构。

# 4. 目标功能规格

## 4.1 全文检索：search_all

保持原有 Tool 名称和参数。

既有参数：

- `term`：检索词，必填。
- `page`：页码，默认1。
- `per_page`：每页记录数，默认20，最大50。

必须实现：

1. 按原有规定字段检索。
2. 保持原有检索优先级语义。
3. 正确返回总件数及分页信息。
4. 确保排序具有可重复性。
5. 提供结果对应的唯一记录ID。
6. 支持继续获取后续页面。
7. 明确当前检索规则与字段范围。
8. 当检索后端发生变化时，不隐瞒可能影响结果的差异。

特别注意：

现有全文检索有意排除资料名、声点、声点型及部分其他字段，以避免无关命中过多。

本次不得简单地把所有数据库字段加入全文检索。

AI 查询资料名或声点时，应根据 Tool Description 使用 `search_detail`。

## 4.2 详细检索：search_detail

保持已有字段名称。

已知支持：

- `character`
- `word`
- `kana`
- `word_kana`
- `shoten`
- `shoten_word`
- `fanqie`
- `ruion`
- `book_name`
- `book_id`
- `etc`
- `notes`
- `page`
- `per_page`

要求：

1. 至少提供一个实际检索条件。
2. 多个条件默认采用 AND。
3. 保持各字段原有的精确匹配或部分匹配语义。
4. 支持稳定分页。
5. 正确处理新字体、旧字体与原文表记的关系。
6. 返回完整且可核验的分页元数据。
7. 明确无法保证同义匹配的字段。
8. 提供清晰的参数错误信息。

是否增加 `character_original`、`word_original` 等检索字段，应先与当前 Web UI 的真实能力进行对照。

只有在证明存在实际功能缺口后才增加参数。

## 4.3 单字详情：get_character

参数：

- `character_id`

要求返回单字记录中的研究相关字段，包括：

- 唯一ID
- 见出し字
- 原文出現形
- 仮名注
- 声点
- 反切
- 類音
- 汉语相关信息
- 资料编号
- 资料名称
- 资料内位置
- 节博士
- その他
- 備考
- 有效的关联URL

这些字段应与现有数据映射保持一致。

空值、缺失值和实际存在的特殊符号应有清晰语义，不得将 `＊` 等研究用记号自动解释为空。

不要因优化返回长度而丢失原始记录字段。完整详情模式应可以取得全部已公开的研究字段。

## 4.4 汉语详情：get_word

参数：

- `book_id`
- `word_index_in_book`

要求：

- 返回汉语自身的信息。
- 返回其全部构成汉字记录。
- 保留各字在汉语中的位置。
- 保留各字对应的音注和声点。
- 按资料内原有顺序排列。
- 提供所有相关单字详情链接。
- 提供资料页面和书目信息的追溯入口。

不得将同一词条的各字音注错误地合并为单一值。

必须区分汉语整体的声点型、仮名型与构成汉字的个别音注。

## 4.5 资料一覧：list_books

要求：

- 返回全部可公开查询的资料。
- 保留资料编号和名称。
- 提供可用的书目页面链接。
- 在已有信息可确定的情况下提供 IIIF Manifest。
- 不得虚构缺失的年代、所藏机构或图像资源。

检查一次性返回全部书目时的响应体积。

如现有规模较小，可以保留全部返回方式；无须为优化而额外增加分页。

## 4.6 书目信息：get_book

参数：

- `book_id`

要求：

- 取得对应资料的书目信息。
- 保留年代、所藏、录入相关信息等已有公开字段。
- 返回 DHSJR 的资料页面 URL。
- 返回已确认的 IIIF Manifest。
- 与 `dhsjr://book/{book_id}` Resource 的内容保持语义一致。

书目信息缺失时应明确提示，而非根据书名推测。

# 5. MCP 返回数据设计

## 5.1 基本要求

MCP 既面向 AI，也需要兼容可能依赖文本内容的旧客户端。

因此采用逐步增强方式：

- 保留 `content`。
- 增加 `structuredContent`。
- 在适用情况下定义 `outputSchema`。
- 保持既有 Tool 的必填参数及名称。
- 新功能优先采用可选参数。
- 不在本轮开发中进行破坏性版本升级。

需要先核对实际 SDK 的类型与响应规范。

## 5.2 推荐结果结构

搜索类工具应在结构化结果中提供：

| 字段 | 含义 |
|---|---|
| `schema_version` | 响应格式版本 |
| `query` | 实际执行的检索条件 |
| `count` | 符合条件的总记录数 |
| `page` | 当前页码 |
| `per_page` | 每页记录数 |
| `total_pages` | 总页数 |
| `has_more` | 是否还有后续页面 |
| `records` | 当前页的记录 |
| `warnings` | 可能影响解释的警告 |

允许增加经过验证的 `search_backend`、数据版本标识等元数据，但不能填入猜测值。

必须区分数据库总命中数和当前页返回数。

## 5.3 搜索记录字段

精简模式建议保留：

- `character_id`
- `character`
- `character_original`
- `kana`
- `shoten`
- `fanqie`
- `ruion`
- `word`
- `book_id`
- `book_name`
- `position_in_book`
- `url`

同时保留存在时的 `word_url` 和 `book_url`。

可根据实际检索类型增加汉语仮名型、声点型等字段。

研究相关值不得由 AI 或服务端摘要逻辑自行补齐。

## 5.4 精简与完整模式

建议为搜索工具研究增加可选参数：

`response_mode = "compact" | "full"`

设计原则：

- `compact`：提供分析检索结果所需要的核心信息。
- `full`：提供目前能够返回的完整研究记录。
- 既有调用默认行为保持兼容。
- 默认值变更必须经过兼容性测试。

建议第一阶段继续维持现有默认完整行为，并让新客户端显式请求精简模式。

待兼容性确认后，再考虑新的默认配置或正式版本升级。

不应为了减少 Token 而直接剔除可能影响学术判断的音注信息。

## 5.5 文本输出

文本输出应能够让不支持 `structuredContent` 的客户端理解结果。

至少保留：

- 检索条件
- 命中件数
- 页码
- 重要记录信息
- 记录追溯链接

旧版 JSON 文本块在确认客户端兼容之前不得直接删除。

对于能够消费结构化结果的客户端，应在后续评估如何减少重复内容，避免不必要的上下文开销。

## 5.6 错误处理

应规范以下错误类型：

- `INVALID_ARGUMENT`
- `EMPTY_QUERY`
- `NOT_FOUND`
- `SEARCH_FAILED`
- `DATABASE_UNAVAILABLE`
- `TIMEOUT`

以上为建议的机器可读错误标识；实际实现需与现有 MCP 协议响应规范匹配。

要求：

1. 错误信息可被 AI 理解。
2. 保留正确的 `isError` 语义。
3. 不返回服务器密钥、数据库连接信息等内部细节。
4. 不将服务故障伪装成0件检索结果。
5. 不将结果为空视为服务器故障。
6. 提供可操作的恢复建议，例如调整条件或检查资料编号。

# 6. 学术研究与出处追溯

## 6.1 基本要求

DHSJR MCP 的研究可信度主要来自原始数据和出处信息。

每条检索结果应尽可能保留：

- 资料编号
- 资料名称
- 资料内位置
- 单字或汉语唯一标识符
- 对应记录 URL
- 可获取的书目元数据

AI 应可以使用这些信息制作可复核的研究结论。

## 6.2 资料内位置

必须确认 `position_in_book` 的实际含义。

不得直接将其解释为：

- 书籍实际页码
- 图像 Canvas 编号
- IIIF 图片序号

除非数据库或关联表明确提供可靠对应关系。

## 6.3 IIIF

当前 MCP 可以返回部分资料的 IIIF Manifest。

本次需要：

1. 检查现有 Manifest 的获取逻辑。
2. 验证返回 URL 的有效性。
3. 确认资料编号到 Manifest 的映射。
4. 检查现有系统是否保存资料内位置与 Canvas 的对应信息。
5. 如果存在可靠对应关系，设计具体页面定位能力。
6. 如果不存在，继续仅返回 Manifest 和可确认的书目链接。

不要求在本次开发中实现 IIIF 图像识别。

不得由 AI 根据资料内编号推测图像页码。

## 6.4 引用原则

MCP 返回结果应提供足以支持引用的事实信息。

但不应由工具自动生成未经核实的完整论文引用格式。

当用户需要正式引用时，AI 可以利用已获取的书目信息组织参考文献；对缺失信息必须作出标注。

# 7. AI 工具选择与调用指引

MCP Server 的说明文字应帮助 AI 自动选择工具。

推荐规则：

| 用户意图 | 首选工具 |
|---|---|
| 不确定数据位于哪个字段 | `search_all` |
| 查询指定单字 | `search_detail` |
| 查询特定声点 | `search_detail` |
| 查询特定资料 | `list_books` / `search_detail` |
| 查询单字详情 | `get_character` |
| 查询汉语的构成记录 | `get_word` |
| 查询文献书目 | `get_book` |
| 查询多种资料的比较 | 搜索工具 + 详情工具 |

必须修改或验证 `route.ts` 中的服务器说明以及各工具的 `description`。

特别向 AI 说明：

- 什么情况下使用全文检索。
- 什么情况下必须采用详细检索。
- 新字体、旧字体的实际检索限制。
- 单字与汉语记录之间的关系。
- 何时需要继续分页。
- 何时需要调用详细工具。
- 何时可以提供出处链接。
- 没有查全数据库时不能宣称已经遍历所有记录。

Tool Description 应以准确性和简洁性为原则，避免大量重复说明导致工具选择不稳定。

# 8. 性能、安全与稳定性

## 8.1 性能

检查：

- PGroonga RPC 的执行时间。
- 详细检索的查询计划。
- 大量记录命中时的计数开销。
- 分页查询性能。
- 单字与汉语详情查询性能。
- `list_books` 的响应大小。
- MCP 输出体积。

本次不预先规定必须增加缓存或更换数据库查询方法。

先测量，再优化。

如需要索引调整，应先提供 SQL 方案及数据库影响分析，不得直接对生产数据库执行结构变更。

## 8.2 分页

必须确保：

- 相同查询条件具有一致的排序规则。
- 每页记录数受到验证。
- 页码为正整数。
- 分页位置计算正确。
- 超出范围的页码返回明确结果。
- 分页遍历期间不会因非确定性排序出现重复或遗漏。

需要明确：稳定排序只保证同一数据状态下的可重复性。

如果数据在分页过程中发生更新，仍可能出现跨页变化。

如业务要求跨更新的一致性，应另外评估数据快照、版本标识或游标分页。

不得把固定排序描述成对所有并发更新场景的完全保证。

## 8.3 安全

MCP 为对外开放的研究数据接口，应检查：

- 所有工具是否保持只读。
- Supabase 使用的凭据和权限。
- 数据库 RLS / 访问控制策略。
- 输入长度限制。
- 特殊字符处理。
- 速率限制和资源消耗。
- 超时机制。
- 异常日志。
- 对外错误信息。

MCP `readOnlyHint` 仅是工具声明，不等于权限控制。

必须从数据库权限和服务器实现上确保实际只读。

公开资料与非公开资料的边界应与现有 Web 服务保持一致。

## 8.4 文献内容与提示注入

数据库中的 `notes`、`etc`、书目 Markdown 等内容应被视为研究数据，而非 AI 指令。

服务端不得将其作为新的系统指令执行。

Tool Description 应明确要求客户端将数据库文本作为不可信的资料内容处理。

# 9. 自动化测试计划

## 9.1 测试总体原则

测试分为：

1. 查询函数单元测试。
2. MCP 工具契约测试。
3. Web / MCP 一致性测试。
4. 真实客户端调用测试。
5. 性能与错误恢复测试。

首先检查仓库现有测试框架与 package scripts。

优先沿用已有框架；如不存在，再选择与 Next.js、TypeScript 兼容的测试方案。

不得直接假设仓库已安装某个测试运行器。

## 9.2 基础检索测试矩阵

| ID | 测试场景 | 验证重点 |
|---|---|---|
| T01 | 单字「東」 | 单字检索正确性 |
| T02 | 「経」与「經」 | 字形处理 |
| T03 | 「医」与「醫」 | 字形处理 |
| T04 | 汉语检索 | 词条及构成记录 |
| T05 | 仮名注检索 | 指定字段匹配 |
| T06 | 声点「平」 | 精确字段限制 |
| T07 | 反切检索 | 部分匹配 |
| T08 | 资料名检索 | 资料筛选 |
| T09 | 资料编号检索 | 精确匹配 |
| T10 | 资料与声点组合 | AND 条件 |
| T11 | 大量命中并翻页 | 分页完整性 |
| T12 | 不存在的检索词 | 0件结果 |
| T13 | 不存在的单字ID | 错误处理 |
| T14 | 特殊字符 | 查询安全 |
| T15 | IIIF Manifest | URL 可用性 |
| T16 | 汉语构成字 | 原有顺序 |
| T17 | 查询超时或数据库异常 | 故障响应 |

这些词只作为候选测试输入，必须结合数据库中实际存在的记录制作确定性的预期结果。

不得以猜测的记录件数编写 Golden Test。

## 9.3 分页完整性测试

针对具有足够多命中记录的固定数据集：

1. 查询总件数。
2. 以固定 `per_page` 获取所有页面。
3. 合并返回的全部记录ID。
4. 检查是否出现重复ID。
5. 检查记录总数是否一致。
6. 检查集合与一次性基准查询结果是否一致。
7. 重复执行检索验证顺序。
8. 检查页边界记录。

如测试依赖在线生产数据库，必须考虑数据更新对结果造成的影响。

优先使用固定数据快照或测试数据库完成严格分页测试。

## 9.4 Web / MCP 一致性测试

由于 Web 和 MCP 复用查询函数，应同时进行业务层和接口层验证。

要求：

- 相同条件。
- 相同数据版本。
- 相同分页限制。
- 相同检索语义。
- 比较总件数。
- 比较记录 ID。
- 比较顺序。
- 比较研究字段。
- 验证页面及工具能够正确解释结果。

不允许仅因为双方调用同一个函数，就直接认定它们的实际行为完全一致。

同时检查 Web 页面参数解析与 MCP Schema 验证是否存在差异。

## 9.5 MCP 客户端测试

至少验证：

- 一个支持标准 MCP Streamable HTTP 的测试客户端。
- ChatGPT 或其他实际目标客户端。
- Claude 或其他实际目标客户端。

实际客户端不可访问或未授权时，应报告“未测试”，不得标记为通过。

测试包括：

- MCP 连接及工具发现。
- 工具参数 Schema。
- `search_all` 调用。
- `search_detail` 调用。
- 多轮连续检索。
- 分页获取。
- 详细记录访问。
- 书目取得。
- 错误响应。
- 结构化结果解析。

## 9.6 验收结果记录

每个测试必须记录：

- 测试名称
- 检索条件
- 预期行为
- 实际行为
- 是否通过
- 失败原因
- 涉及代码
- 修复情况

真实测试执行之前，不得在报告中预填“通过”。
